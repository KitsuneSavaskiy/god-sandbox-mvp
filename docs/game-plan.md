# GodSandbox game plan

この文書は、GodSandbox のゲーム方針正本です。

Codex / Claude / 監査役 / 将来の参加者は、UI、docs、sample、prototype を作る前に、この文書の前提から外れていないか確認します。

## 1文説明

GodSandbox は、AIキャラクターが暮らす小さな箱庭を新米神様として見守り、出来事に対して「見守る / 助ける / 試練を与える」を選び、成長したキャラクターを外へ持ち出せる育成サンドボックスです。

## 役割

### Product Owner / 制作者

- PO は、このゲームの制作者です。
- PO 自身は作中キャラクターとして登場しません。
- PO の個人画像、個人設定、ローカルパス、secret、API key、token は Git 管理に入れません。

### プレイヤー

- プレイヤーは「新米神様」です。
- プレイヤーの姿や人格は、プレイヤー自身に委ねます。
- プレイヤーは小さな箱庭世界を見守り、住民の変化に気づき、必要な時だけ介入します。

## Main Loop

1. 箱庭を見る。
2. 住民や変化に気づく。
3. イベントで関わり方を選ぶ。
4. 住民が変化・成長する。
5. 育ったキャラクターを Character Passport として外へ持ち出せる。

## 関わり方

| 表示 | 初見向け説明 | 役割 |
| --- | --- | --- |
| Watch | 見守る | 状況を知り、記録を増やす |
| Bless | 助ける | 命や成長を支える |
| Test | 試練を与える | 危険を伴う成長機会を作る |

初見ユーザーには、いきなり内部用語や実装語を出しません。

- `tick` は「少し時間を進める」と言い換える。
- `介入` は「どう関わるか選ぶ」と言い換える。
- `schema`、`domain model`、`provider`、`Passport schema` は、初回導線では出さない。

## Sprint5方針

Sprint5 の目的は、初見ユーザーが最初の数分で次を理解できる状態に近づけることです。

- 何のゲームか。
- 何をすればよいか。
- Bless で何が起きるか。
- 育ったキャラクターを外へ持ち出せること。

優先順位:

1. Web公開MVPとして、iPhone Safari / Android Chrome / PCブラウザで遊べる状態を優先する。
2. 初見ユーザーの「最初に押す場所」を明確にする。
3. 使徒の短い案内と、操作場所のハイライトで導く。
4. App Store / TestFlight / Capacitor / PWA本格対応は後続に回す。

## Web公開MVP方針

- まずはブラウザで遊べることを正本にする。
- iOS MVP は App Store 審査を前提にせず、Safari から公開URLを開く方針にする。
- Android MVP は Chrome から公開URLを開く方針にする。
- ホーム画面追加は任意導線です。
- Capacitor、native project、PWA manifest、Service Worker は後続PBIで判断する。

## UI変更の確認ルール

UI変更は、`npm run build` 成功だけで完了にしません。

UIに触るPRでは、可能な範囲でブラウザ確認を行い、PR本文に結果を書きます。

最低確認:

- PC幅で大きく崩れていない。
- iPhone相当の縦幅で主要CTAが見える。
- 重要操作がタップしやすい。
- 横スクロールが必要な場合、どこが横スクロールするか画面上で分かる。
- 初見導線に `tick` や `schema` などの技術語が出ていない。

ブラウザ確認できなかった場合:

- できなかった理由をPR本文に書く。
- 代替確認として、スクリーンショット、Playwright、手元ブラウザ、または実機確認のどれを未実施にしたか明記する。

## アートプロンプト保存ルール

アート生成や画像差分のプロンプトは、Git管理する場合 `docs/art-prompts/` に置きます。

- ファイル名は、対象PBIや用途が分かる名前にする。
- secret、個人画像、個人設定、個人ローカルパスを含めない。
- 生成に使った外部サービス名やmodel名を書く場合は、必要な範囲に留める。
- 実画像ファイルは、PBIで許可された asset / public / sample の範囲にだけ追加する。

## ローカルログと補助ファイル

`.logs/` は勝手に追加しません。

理由:

- ローカル作業ログは個人環境情報や一時出力を含みやすい。
- secret scan や監査対象を増やす。
- PBI成果物ではないファイルがPRに混ざりやすい。

ログや補助メモが必要な場合:

- Git管理外のローカルファイルに置く。
- PRへ入れる必要がある場合は、PBI scope として明示し、secretや個人情報を除去する。
- `.gitignore` 追加が必要な場合も、PBIとして分ける。

## GodSandbox用レビューseverity

監査役は、GitHub PR diff / changed files を正本にして判断します。

| severity | 使う場面 |
| --- | --- |
| P0 blocker | secret漏えい、個人情報混入、package/CIの無許可変更、起動不能、データ破壊、重大なscope逸脱 |
| P1 blocker | 受け入れ条件の主要未達、初見導線を壊すUI、スマホで主要操作不能、Passport contract破壊、レビュー必須scopeの未確認 |
| P2 non-blocker | merge前に直すとよい不整合、文言誤解、軽いレイアウト崩れ、follow-upなしだと後で迷う設計 |
| P3 follow-up | 今回scope外の改善案、将来のUX調整、軽微な説明補足 |

blocker がある場合は merge しません。

blocker ではない指摘は、今回直すか follow-up PBI に分けるかを明記します。

## 実装時の禁止

- ついで修正をしない。
- package変更を混ぜない。
- CI workflow変更を混ぜない。
- server変更を混ぜない。
- Passport schema変更を別PBIに混ぜない。
- POの個人情報、画像、ローカルパス、secretを入れない。
- GitHub上では MR ではなく PR と呼ぶ。
